## 0. Общее для всех трёх функций

### 0.1 Где хранить настройки
У нас уже есть общий key-value в `Core::Settings`: `writePref<T>(key, value)` / `readPref<T>(key, fallback)` (core/core_settings.h:1047-1060, хранится в хвосте сериализации core_settings.cpp:1035-1050, поэтому формат файла настроек не ломаем и новые поля в бинарный поток не добавляем).
Предложение: новый модуль `mokagram/mokagram_ghost.h/.cpp` (namespace `Mokagram::Ghost`), в `Telegram/CMakeLists.txt` добавить рядом с `mokagram/plugins/*` (строки 73-80).
Что в модуле:
- четыре флага: `hideRead`, `hideOnline`, `hideTyping`, `hideStoryViews` (+ опционально `hideBlocked` для п.2 и `showPackOwner` для п.3) в `rpl::variable<bool>`;
- чтение один раз на старте из `Core::App().settings().readPref<bool>("mokagram.ghost.read", false)` и так далее, дальше горячий путь читает только кэш-переменную (`bool` из `rpl::variable::current()`), без поиска по flat_map на каждый вызов;
- сеттер пишет pref и вызывает `Core::App().saveSettingsDelayed()` (core/application.h:225);
- события выключения/включения идут через `rpl::producer`, никаких таймеров.
Настройки глобальные, не по аккаунтам (у AyuGram по аккаунтам, нам для первой версии это лишнее).

### 0.2 UI переключателей
Экран: `settings/sections/settings_privacy_security.cpp` (секция приватности) отдельным блоком «Призрак» либо отдельная секция. Это решение владельца и скилла tier-ios-ui/дизайна, здесь только точка: компонент строки-переключателя как в соседних блоках этого файла. Быстрый переключатель (иконка-призрак в боковом меню/трее) - отдельная задача.

### 0.3 Принцип врезки: защита на уровне приложения, а не на уровне MTProto
Есть соблазн резать запросы одним фильтром в `Instance::Private::sendRequest` (mtproto/mtp_instance.cpp:1021) по id конструктора (messages.readHistory и т.д.). Не делать так. `Data::Histories::sendRequest` (data/data_histories.cpp:1066) ставит запросы по истории в очередь и ждёт `finish` каждого. Если запрос молча проглочен на уровне MTProto, `finish` не вызовется, очередь истории встанет, и перестанут уходить следующие запросы по этому чату (в том числе отправка сообщений). Так же зависнет выход из приложения (quitPreventFinished в done/fail). AyuGram режет именно в приложении, до постановки запроса, и мы так же.
Исключение: хук `pre_request_hook` из SPEC.md плагинов можно использовать как резервную сеть, но не как основной механизм.

## 1. Режим призрака

### 1.1 Как это сделано в AyuGram (поведение)
Настройки на аккаунт: `sendReadMessages`, `sendReadStories`, `sendOnlinePackets`, `sendUploadProgress`, `sendOfflinePacketAfterOnline`, `markReadAfterAction`, `useScheduledMessages` + общий переключатель режима и «замки» на каждый флаг. Подавляются запросы:

| Что скрываем | MTP-запрос | Где у них гасится |
|---|---|---|
| «Прочитано» в чатах | `messages.readHistory`, `channels.readHistory` | `Histories::sendReadRequests` в начале: если нельзя, таймер отменяется, у всех состояний обнуляются `willReadTill/willReadWhen`, вызывается `checkEmptyState`, выход |
| «Прочитано» в комментариях/топиках-обсуждениях | `messages.readDiscussion` | `RepliesList::sendReadTillRequest`, ранний выход после отмены таймера |
| Прослушано голосовое, просмотрен кружок, открыто медиа с TTL | `messages.readMessageContents`, `channels.readMessageContents` | оба `ApiWrap::markContentsRead`: пропуск, кроме «проходных» случаев (непрочитанное упоминание или реакция без непрочитанного медиа) |
| «В сети» | `account.updateStatus` | `Updates::updateOnline`: флаг «онлайн» для сервера = `sendOnlinePackets && реальноОнлайн`, но локальное состояние `_lastWasOnline` ведётся по реальному |
| «Печатает», «записывает», «загружает» | `messages.setTyping` | `SendProgressManager::send` после `skipRequest`: если `sendUploadProgress` выключен, ранний выход. Гасит ВСЕ типы, включая typing |
| Просмотр историй | `stories.readStories`, `stories.incrementStoryViews` | `Stories::markAsRead`, `sendMarkAsReadRequest`, `sendMarkAsReadRequests`, `sendIncrementViewsRequests`, `isQuitPrevent`: везде ранний выход |
| «Не показывай, что я онлайн после того как был» | `account.updateStatus(offline=true)` | `AyuWorker`: таймер раз в 3 секунды, шлёт offline, если сервер видит нас онлайн. Мы это НЕ повторяем (см. 1.4) |
| «Прочитано при отправке» | служебное | `markReadAfterAction` в apiwrap и data_histories: после отправки сообщения всё же отправить read |
| Отправка через отложенные | `messages.sendMessage` со `schedule_date` | `applyGhostScheduling` в apiwrap: в режиме призрака сообщения уходят как отложенные, чтобы не раскрыть чтение. Вне объёма этой спеки |

Дополнительно AyuGram в ленте скрывает чужой индикатор печати от заблокированных (`FiltersController::isBlocked` в `history_view_send_action.cpp`), это относится к п.2.

### 1.2 Точки врезки в нашем коде

Везде условие: `Mokagram::Ghost::...()` возвращает true, если соответствующая функция скрытия включена.

1. Прочитано в чатах.
   - `data/data_histories.cpp:720` `Histories::sendReadRequests()`: в самом начале, если `hideRead`: `_readRequestsTimer.cancel()`, собрать список историй из `_states`, обнулить `state.willReadTill` и `state.willReadWhen`, затем `checkEmptyState(history)` для каждой (собирать в вектор, `checkEmptyState` меняет `_states`, нельзя менять контейнер во время обхода), `return`.
   - Прямые вызовы сервера: `sendReadRequest` (:747) вызывается только из `sendReadRequests` (проверить grep перед правкой; есть вызовы `sendReadRequests()` из :330, :663, :773, все идут через ту же функцию).
   - Локальное состояние (счётчик непрочитанных падает на экране) остаётся как есть: клиент считает чат прочитанным, сервер не знает. После перезапуска счётчики вернутся с сервера, это нормально и ожидаемо.
   - Двойная проверка не нужна, одна точка покрывает `readInbox`, `readInboxTill`, `readInboxOnNewMessage`.
2. Прочитано в обсуждениях: `data/data_replies_list.cpp:1001` `RepliesList::sendReadTillRequest()`: после отмены `_readRequestTimer` и `_readRequestId` выйти до `MTPmessages_ReadDiscussion` (:1008).
3. Содержимое (голосовые, кружки, TTL): `apiwrap.cpp:1440` и `:1472` оба `ApiWrap::markContentsRead`. Внутри цикла после `item->markContentsRead(true)` (локальная пометка остаётся) пропускать добавление id в запрос. Для одиночной версии выход перед `request(...)`. Оставить «проходной» случай, как у AyuGram: непрочитанные упоминание или реакция должны сниматься на сервере (иначе у собеседника не изменится ничего, а у нас навсегда висит бейдж), но это решение владельца, по умолчанию повторить их.
4. В сети: `api/api_updates.cpp:993` `Updates::updateOnline(crl::time, bool)`.
   - Не менять `isOnline` и `_lastWasOnline` (строки ~996-1030, `_lastWasOnline = isOnline` на :1026). От `_lastWasOnline` зависят задержка уведомлений (`window/notifications_manager.cpp:400`, `lastWasOnline()`) и `isQuitPrevent` (:1086). Если подменить само `isOnline`, при включённом телефоне уведомления на десктопе начнут задерживаться как у «не в сети» клиента.
   - Менять только отправку: перед `api().request(base::take(_onlineRequest)).cancel()` на :1023 (и далее до :1038) при включённом `hideOnline` и `!Core::Quitting()` не слать `account.updateStatus` вообще. При `Core::Quitting()` слать `MTP_bool(true)` (offline) с теми же `done/fail` колбэками, иначе `quitPreventFinished()` не вызовется и приложение зависнет на выходе.
   - Одноразовый сброс: в сеттере `hideOnline` при включении один раз на каждую сессию отправить `account.updateStatus(offline=true)` (сервер считает нас онлайн ещё минуты после последнего реального online), затем `session->updates().updateOnline()` (публичный, :981) для пересчёта локального состояния. При выключении то же `updateOnline()` вернёт онлайн штатно.
   - Это событийная схема: ни таймера на 3 с, ни опроса. Периодический таймер `_onlineTimer` в tdesktop уже есть и свой, мы его не добавляем.
5. Печатает: `api/api_send_progress.cpp:55-75` `SendProgressManager::update(history, topMsgId, type, progress)`: после проверки self/канала добавить `if (hideTyping && progress >= 0 && type != SendProgressType::Speaking) return;`. Ставить в `update`, а не в `send` (:111) как AyuGram: тогда не заводятся записи в `_updated` и таймеры отмены. Отмену (`progress < 0`) пропускать как есть, она безвредна. Тип `Speaking` (голос в звонке) оставить: это не «печатает», его скрытие ломает интерфейс групповых звонков (решение, не копия AyuGram).
   - Побочные каналы, которых у AyuGram нет: `chat_helpers/emoji_interactions.cpp:323` и `:480` (`sendMessageEmojiInteraction` и `...Seen`, раскрывает, что мы смотрим анимацию эмодзи в чате) и `history/history_streamed_drafts.cpp:342` (`StopDraftAction`, только для ботов со стримом). Для первой версии ставить под тот же флаг `hideTyping`: ранний выход в начале `sendAccumulatedOutgoing` (:295) и `checkSeenRequests` (:420).
6. Истории:
   - `data/data_stories.cpp:1235` `Stories::markAsRead`: после проверки «это мои истории» (:1236) при `hideStoryViews` вернуться до `lookup`. Это же покрывает `_incrementViewsPending` (:1246) и `bumpReadTill`, то есть локальный «прочитанный» круг останется непрочитанным (так у AyuGram, это ожидаемо).
   - Дублирующие предохранители от ранее набранных очередей: `sendMarkAsReadRequest` (:1394), `sendMarkAsReadRequests` (:1424), `sendIncrementViewsRequests` (:1440) и `isQuitPrevent` (:2286). В последнем при `hideStoryViews` вернуть false, иначе выход ждёт запросов, которых нет. Достаточно ранних `return` в начале каждой.
   - Свой «режим скрытности» сервера (`stories.activateStealthMode`) не используем, он платный по премиуму и не наш случай.
7. Отметка «прочитано после отправки» (`markReadAfterAction`): по умолчанию выключена. Отправка сообщения сама вызывает `readInbox` (apiwrap.cpp:3860 и :3955), он упрётся в п.1 и не уйдёт.

1. Модуль `mokagram_ghost` + CMake + pref-ключи.
2. Врезки п.1.2/1-3 (чтение): три файла, около 25 строк.
3. Врезка п.4 (онлайн) с одноразовым сбросом.
4. Врезка п.5 (печать), п.6 (истории).
5. Экран переключателей и реакция на выключение: при выключении `hideRead` для текущего открытого чата вызвать `session().data().histories().readInbox(history)`, остальные чаты прочитаются, когда пользователь в них зайдёт.
6. Проверка (после сборки владельцем, не раньше): второй аккаунт или Telethon-сессия наблюдает: нет галочек «прочитано», нет «печатает», нет «в сети», в историях нет нашего просмотра; в логах запросов нет `readHistory/setTyping/updateStatus(online)/readStories`.

### 1.4 Чего НЕ делаем
- Таймер раз в 3 с (AyuWorker) не повторяем. Он нужен им, чтобы перебить статус «онлайн», который выставил другой клиент или сервер. Наш одноразовый сброс при включении и отсутствие `updateStatus(online)` дальше покрывают задачу. Остаточный эффект: если тот же аккаунт онлайн в другом клиенте (телефон), статус «в сети» будет от него, мы это не контролируем.
- Блокирующей работы в потоке интерфейса нет: все врезки это булевые проверки и ранние выходы, запрос `updateStatus` при включении асинхронный (`.send()`).

### 1.5 Риски
- Отправка сообщения. По моим сведениям сервер Telegram сам считает диалог прочитанным, когда мы отвечаем в него. Это не проверено на 7.3.3 и не может быть подавлено нашей врезкой. Если подтвердится, единственный обход у AyuGram это отправка отложенным (`useScheduledMessages`). Решать с владельцем, в первую версию не входит.
- Счётчики непрочитанных после выхода на другом устройстве: сервер шлёт `updateReadHistoryInbox`, и локальные «прочитано» могут сброситься. Это штатно.
- Голосовые и кружки: пока `markContentsRead` на сервер не ушёл, у отправителя нет «прослушано», а у нас локально проигрываемое помечено. Следствие: при смене устройства голосовое снова «новое».
- Уведомления: сохраняя `_lastWasOnline` реальным, мы не меняем логику задержки уведомлений (п.4). Если кто-то решит подменять `isOnline`, это сломается.
- `Histories::sendReadRequests` вызывается и из других веток (:330, :663, :773). Единая ранняя защита в начале функции покрывает их все, но при правке проверить, что обнуление `willReadTill` не оставляет `state.sentReadDone` в промежуточном положении (читать `checkEmptyState`, :795).
- Слой схемы: новые типы send-action могут появиться в обновлениях tdesktop. Защита в `update()` по `progress >= 0` и типам не зависит от списка action, поэтому устойчива.

## 2. Полное скрытие сообщений заблокированных пользователей

### 2.1 Как это сделано в AyuGram (поведение)
Настройка `hideFromBlocked` (внутри системы фильтров, работает только при включённых фильтрах). Единый предикат `filtered(item)`:
- не применяется к своим исходящим;
- сообщение скрыто, если автор `user->isBlocked()`, но НЕ когда это личный диалог с самим заблокированным (иначе пустой чат); тот же признак для оригинального автора пересланного и для `via_bot`;
- не применяется, если пользователь временно включил «показать скрытые» в этом чате.
Применение (в ядре они подключают предикат в нескольких местах):
1. `HistoryItem::isEmpty()` возвращает true для скрытого сообщения. Это и есть главный приём: вид сообщения схлопывается так же, как у пустых сообщений (высота 0, не участвует в датах и «непрочитанных»), без отдельной ветки отрисовки.
2. `HistoryItem::toPreview` возвращает пустой превью: превью в списке чатов, в поиске и в ответах не светит текст.
3. Строка ответа (`history_item_components.cpp`, reply-to) не показывает скрытое сообщение как цитату.
4. Список чатов: `dialogs_layout`, `dialogs_row` (имя автора в результатах поиска).
5. Реакции и «кто прочитал»: блокированные убираются из списков и счётчика.
6. Индикатор «печатает» от заблокированных не показывается.
7. Комментарии под постом: аватарки комментаторов (`history_view_message.cpp`) фильтруются.
8. Обновление: при изменении признака блокировки (`PeerUpdate::Flag::IsBlocked`) `HistoryWidget` и `ListWidget` принудительно пересчитывают размеры и перестраивают строки (`forceFullResize`, `setPendingResize` + `refreshRows`).
9. Кэш: после редактирования сообщения кэш предиката инвалидируется.

### 2.4 Риски
- Счётчик непрочитанных: сервер считает сообщения заблокированных непрочитанными, мы их скрыли. Бейдж может показывать число без видимых сообщений. У AyuGram так же. Решение: либо принять, либо `Histories` должен автоматически считать скрытые прочитанными (опасно, затрагивает п.1, не делать в первой версии).
- Группировка альбомов: если часть альбома скрыта, `HiddenByGroup` и `isEmpty` дают смешанное состояние. Альбом одного автора скрывается целиком (автор один), пересылаемые альбомы с разными оригинальными авторами могут скрыться частично. Проверить на реальном альбоме.
- Пустые «хвосты»: дата и разделитель «непрочитанные» привязаны к первому непустому элементу (`history_view_element.cpp:3193, 3214`). Эти функции уже учитывают `isEmpty()`, значит должны работать, но проверять визуально на заполненном экране.
- `isEmpty()` меняет семантику для других потребителей (например `isGroupMigrate()` в history_item.h:327 использует `isEmpty()` вместе с флагом `IsGroupEssential`; скрытые сообщения этим флагом не обладают, коллизии нет).
- Личные диалоги: заблокированный пользователь не может нам писать, но старая история есть. Диалог с ним не скрываем (иначе чат пустой), скрываем его сообщения только в группах и каналах-обсуждениях, как AyuGram.
- Горячий путь: если `from()` ещё не загружен или `isBlocked()` в состоянии `Unknown`, считаем «не заблокирован». Состояние блокировки приходит позже (`BlockStatus::Unknown` на `data/data_peer.h:663`), поэтому нужна переоценка по `IsBlocked` (п.4).

## 3. Владелец пака стикеров и эмодзи

### 3.1 Формула у AyuGram
Функция `getUserIdFromPackId(uint64 id)` (ayu/utils/telegram_helpers.cpp, ссылается на коммит TDesktop-x64/tdesktop PR 218). Поведение:
1. старшие 32 бита id набора = базовое значение id пользователя: `owner = id >> 32`;
2. если байт `(id >> 16) & 0xff` равен `0x3f`, то к `owner` добавляется бит `0x80000000` (id пользователя не умещается в 31 бит);
3. если байт `(id >> 24) & 0xff` не ноль, то к `owner` прибавляется `0x100000000` (id пользователя больше 2^32, из верхних разрядов, захваченных в нижних байтах id набора).
Возвращает 0/пустое значение, если id набора в старших 32 битах пуст (тогда владельца нет). Это эвристика из наблюдений за тем, как Telegram собирает id набора (id пользователя в старших разрядах + случайная часть), а не документированное API. Результат нужно показывать как «вероятный владелец».
Файл-эталон поведения для проверки на тест-векторах: нужен набор известного автора, для которого сверяем `id_set -> id_user`; тест-векторов в репозитории AyuGram нет, их надо собрать руками (три-четыре пака, владельца которых владелец проекта знает).

### 3.2 Где показывает AyuGram
Только в контекстном меню сообщения, в подменю «Детали сообщения»: строка «Владелец пака» с подписью-значением (сначала «загрузка», потом имя пользователя, если известен; иначе ID с копированием по клику).
- для стикера: `document->sticker()->set.id`;
- для сообщения ровно с одним паком кастом-эмодзи: id единственного пака.
Поиск пользователя по id у них сейчас выключен (функция `searchPeer` заглушена, раньше она слала id стороннему боту через инлайн-запрос). Работает только `userLoaded(id)` из кэша. Мы так же НЕ шлём ничего стороннему боту: это утечка данных.

### 3.3 Точки врезки в нашем коде
1. Формула: новая функция `Mokagram::PackOwner::fromSetId(uint64) -> UserId (0 если неизвестно)` в `mokagram/mokagram_pack_owner.h/.cpp`. Чистая функция без побочных эффектов: тестируется отдельно.
2. Контекстное меню сообщения со стикером: `history/view/history_view_context_menu.cpp:434` `AddDocumentActions`, место сразу после строки «Информация о наборе/Добавить набор» (:468-473, условие `document->sticker() && document->sticker()->set`). Добавить пункт «Владелец пака» с иконкой `st::menuIconStickers`.
3. Контекстное меню кастом-эмодзи: `history/view/history_view_context_menu.cpp:2868` `AddEmojiPacksAction(menu, packIds, source, controller)`: если `packIds.size() == 1`, добавить такой же пункт (id набора в `packIds[0].id`). Вызывается с :1935, :2231, :2629, :2795.

Окно набора (главное место «инфо о паке»): `boxes/sticker_set_box.cpp:1078` блок меню `if (!_inner->shortName().isEmpty())`, внутри `top->setClickedCallback`, после «Копировать ссылку» (:1088-1103). id набора доступен как `_inner->setId()` (используется в :1064). Пункт работает и для эмодзи-наборов и для масок. Если набор свой (`_amSetCreator`, :1239), пункт не показывать.

### 3.5 Риски
- Формула эвристическая: для паков, созданных ботами, старыми аккаунтами или после смены схемы id может дать «чужой» или несуществующий id. Подпись «вероятный владелец», не «владелец».
- Приватность: показываем только то, что вычислили локально и что уже есть в кэше, ничего никуда не отправляем.
- Для кастом-эмодзи, у которых в сообщении больше одного набора, пункт не показываем (как AyuGram), иначе пришлось бы выбирать.
- Тип: `StickerSetIdentifier.id` это `uint64`, возвращаемое значение держим в `int64`/`UserId` аккуратно, сдвиги только по беззнаковому (на знаковом `>>` ведёт себя иначе).
